The answer to your question is: almost, but not on its own. I read "validates every hop, as it does `Host`" as what my reader does with `Host`: well formed **and** naming the configured origin (or scheme), with the `Host` check kept. Under that reading:

- the four rejection cases agree (`forwarded-proto-url`, `-crlf`, `-empty-hop`, `forwarded-host-malformed-hop`);
- two binding cases are refused: `forwarded-host-hop` (`Host: internal:8080`, `X-Forwarded-Host: api.example.com, proxy:8080`) and `forwarded-proto-hops` (`https, http`).

The fixture's reading is that a hop only has to be well formed, and that `Host` is no longer compared with the origin once a trusted proxy is configured. Both are reasonable. The sentence just doesn't choose. A wording that would have led me there:

> In `http_server_adapter`, `config.trusted_proxy: true` means the request arrived through a proxy the server trusts. The adapter then takes the public authority and scheme from the first hop of `X-Forwarded-Host` and `X-Forwarded-Proto` instead of `Host`, and requires every hop to be a well-formed authority or scheme token. It does not compare `Host` with the configured origin.

"First hop" is my inference from `forwarded-host-hop`, so please correct it if the intent is different.
