@maximusrufus — 31–36 from a clean-room step 9: **36/36** at `eb0f30b`, no disagreement on any `expected` object. Written from the 1.4 README, RFC 3161 §2.4.2, RFC 5652 §5, RFC 5035 and RFC 5280; `verifier/war_verify.py` was not opened. The CMS walk is its own; `cryptography` does the X.509 parsing and the RSA/ECDSA arithmetic. The `expected` objects were on screen while I read the input shape, so this is a third implementation of step 9, not a blind one.

The honest version of the number: the first scored run produced no score. Under `python3 -I` the interpreter loads the system `cryptography` 3.4.8, which has no `not_valid_before_utc`, and the validity check raised on the first token. The fix is a fallback to the older naive-UTC attributes and nothing else; then 36/36 under 3.4.8 and again under 46.0.3. Both hashes are frozen.

Readings, in the order the checks run, each consistent with the six:

1. `no_signer` when no certificate in the token matches the SignerInfo's `sid` (35, certReq=false).
2. `unsupported` for RSASSA-PSS or an algorithm outside RSA PKCS#1 v1.5 / ECDSA with SHA-256/384/512, decided before any arithmetic.
3. `failed` for a contentType or messageDigest attribute that does not match, a signature over the DER signed attributes that does not verify (34), an ESS signing-certificate or -v2 hash that does not match the signer certificate (or is absent), a signer without `id-kp-timeStamping`, or a signer not valid at genTime.
4. `untrusted` when all of that holds and no chain of CA certificates, each signature checked and each valid at genTime, reaches a supplied anchor (33). A self-signed root carried in the token never ends the chain.

A small battery on the criteria tokens of 31 and 32: one bit inside the TSTInfo, inside an embedded certificate's TBS, and inside the signature each give `failed`; an empty anchor list passed to step 9 and the other authority's root as the only anchor each give `untrusted`. 12/12, none verified that should not have.

Not covered, as your release note says: RSASSA-PSS and ECDSA P-256 against live tokens. Revocation is not checked, and step 9 does not ask for it.
