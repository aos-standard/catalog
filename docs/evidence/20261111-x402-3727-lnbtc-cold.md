An independent run of these vectors, from outside the project, of the same kind as the one on #4066. I wrote two readers from `scheme_exact_lnbtc.md` and the Layout, Inputs and Expectations sections of `vectors/README.md` only (no SDK code, not the spec's "Request Binding Test Vectors" section, not "Case groups" or "Not covered"), froze them, and scored them once against `exact_lnbtc.json` at `63d5640`. Expectations and notes were stripped until the freeze; the ids and input values were seen. The scoring script was rewritten once: its first version misread the shape of `open` outcomes and of the per-step settlement expectations, and crashed before printing a score. The readers and their run were not changed after the freeze (`FROZEN.txt`). JCS, BOLT11 and secp256k1 recovery are written from their documents, standard library only.

**194/199** cases give the same outcome, 192 with the same reason. `http_binding`, `mcp_binding` and `client` agree on every case. Record: [`docs/runs/x402-lnbtc-cold/`](https://github.com/aos-standard/catalog/tree/6164cb4/docs/runs/x402-lnbtc-cold). CC0.

Three observations, in case they help before other SDKs load the file:

**1. Five adapter cases assume a trusted proxy that the inputs do not mention.** `forwarded-host-hop` expects the authority from `X-Forwarded-Host`, and `forwarded-proto-url`, `-crlf`, `-empty-hop` and `forwarded-host-malformed-hop` expect a malformed hop to be rejected. The text says the server reconstructs the origin "only from trusted proxy information when behind a proxy", but each case's `config` has only `public_origin` and `bound_headers`. My reader took these headers as untrusted and did not read them, so it missed all five. A `trusted_proxy` member in `config`, or one sentence under Inputs, would let a reader from the text get them right.

**2. "Strictly decode" is pinned by cases more than by text.** `invoice-nonzero-padding` expects `invalid_exact_lnbtc_invoice_decode_failed`. My reader does not check the padding bits of a 52-character `p` field, so it rejected the case later, as `invalid_exact_lnbtc_invoice_payee_mismatch`. Same outcome, but the spec does not list what strict BOLT11 decoding includes. Separately, `request-origin-not-configured` got the `reject` outcome with the binding reason rather than `invalid_exact_lnbtc_request_mismatch`, since the text gives no local reason for binding failures.

**3. Seven rules that no case reaches.** Changing one rule of the frozen readers at a time, 26 of 36 changes are caught. Not reached: JCS member order by UTF-16 code units, duplicate member names in `params_json`, `NaN`/`Infinity` in `params_json` (no case contains them; several parsers accept them by default, as Python's did for `json-nan` on #4066), an inline `d` beside the description hash, a `p`-multiplier amount not ending in 0, a second `p` field, and the client's check of `requestBindingParams.server` against its intended MCP server. [`runs/candidates_63d5640.json`](https://github.com/aos-standard/catalog/blob/6164cb4/docs/runs/x402-lnbtc-cold/runs/candidates_63d5640.json) has one `mcp_binding` case each for the first three, in the file's layout. The expectations are my reading, not agreed.
